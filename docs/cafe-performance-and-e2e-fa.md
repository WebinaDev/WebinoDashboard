# کارایی بردهای زنده و تست‌های سرتاسری کافه

تاریخ: ۲۰۲۶-۱۱-۲۴ · شاخه: `arena/c301587d-webinodashboard`

این سند بند «زیر ۲ ثانیه» و «تست Playwright برای پوز/آشپزخانه» از سند الزامات را می‌بندد و
صادقانه می‌گوید چه چیزی **اندازه‌گیری شده** و چه چیزی **اندازه‌گیری نشده** است.

---

## ۱. چه چیزی کند بود

هر سه صفحهٔ عملیاتی (آشپزخانه، تابلوی سفارش‌ها، سالن/ارسال) با polling کار می‌کنند:
KDS هر ۸ ثانیه، تابلوی سفارش‌ها هر ۱۰ ثانیه، سالن هر ۱۵ ثانیه، ارسال هر ۲۰ ثانیه.

دو هزینهٔ واقعی پیدا شد:

| مشکل | اثر | اصلاح |
|---|---|---|
| مسیریابی ایستگاه برای **هر آیتم** جدا پرسیده می‌شد (محصول، بعد دسته، بعد ایستگاه پیش‌فرض) | برای یک برد ۴۰ آیتمی روی سه ایستگاه ≈۱۲۰ کوئری، هر ۸ ثانیه، به‌ازای هر صفحهٔ آشپزخانه | `KitchenStations` جدول مسیریابی را یک‌بار در هر درخواست می‌خواند (`routingFor`) — ۲ کوئری، مستقل از تعداد آیتم |
| فیلتر بردها روی ستون‌هایی بود که ایندکس نداشتند (`tenant_id` + `status` + `updated_at`, `table_number`, `delivery_status`؛ و `journal_entry_id` روی سطرهای سند) | filesort روی کل تاریخچهٔ سفارش‌ها در هر poll | مایگریشن `2026_11_25_150000_operations_performance_indexes` (هر ایندکس فقط اگر نبود ساخته می‌شود) |
| ستون‌ها/برچسب‌های KDS هر بار دوباره گرفته می‌شد | درخواست اضافه در هر رفرش | `staleTime: 5 دقیقه` (از قبل بود، حفظ شد) |

علاوه بر این:

- برد آشپزخانه در قطعی شبکه، بلیت‌های ذخیره‌شده را نشان می‌دهد **و** برچسب «به‌روز نمی‌شود»
  را نشان می‌دهد (`data-testid="kds-stale-banner"`). قبلاً فقط قطعی کامل اینترنت بنر داشت؛
  حالا خطای poll هم همان بنر را می‌آورد، چون از دید آشپز هر دو یک چیز است.
- `refetchOnReconnect` روشن شد تا صفحه بعد از برگشت شبکه خودش را تازه کند.

### اندازەگیری

- `KitchenRoutingPerformanceTest` تعداد کوئری‌های مسیریابی ۴۰ آیتم را می‌شمارد و سقف ۳ می‌گذارد.
- **آنچه اندازه‌گیری نشده:** زمان واقعی رندر در مرورگرِ یک تبلت آشپزخانه. این محیط PHP و
  MySQL و مرورگر واقعی ندارد، پس هیچ عدد «۲ ثانیه» یا «Lighthouse» در این سند ادعا نمی‌شود.
  برای گرفتن عدد واقعی: `npm run test:perf` (lhci) روی یک استقرار با دادهٔ واقعی.

## ۲. تست‌های سرتاسری (Playwright)

| فایل | چه چیزی را تضمین می‌کند |
|---|---|
| `frontend/e2e/cafe-pos.spec.ts` | ورود، باز کردن `/dashboard/cafe/pos`، افزودن آیتم، «پرداخت و ثبت»، دیالوگ تسویه، تأیید، و ظاهر شدن بنر سفارش ثبت‌شده **با شمارهٔ واقعی سفارش** + خالی شدن سبد |
| `frontend/e2e/cafe-kitchen.spec.ts` | برد آشپزخانه بلیت نشان می‌دهد، یک بلیت با دکمهٔ «بعدی» جلو می‌رود و **از سرور** همین را تأیید می‌گیرد؛ و با قطع API، بلیت‌ها روی صفحه می‌مانند و بنر کهنگی ظاهر می‌شود |
| `frontend/e2e/admin-sidebar.spec.ts` | (از قبل بود) ناوبری و active دقیق |

برای این تست‌ها `data-testid`های پایدار اضافه شد: `pos-product`, `pos-cart-lines`, `pos-pay`,
`pos-save-open`, `pos-settle-dialog`, `pos-confirm-payment`, `pos-saved`,
`kds-ticket`, `kds-item`, `kds-advance`, `kds-stale-banner`.

### اجرا

```bash
cd frontend
PLAYWRIGHT_BASE_URL=https://your-shop.example \
PLAYWRIGHT_ADMIN_EMAIL=admin@example.com \
PLAYWRIGHT_ADMIN_PASSWORD=•••• \
npm run test:e2e
```

بدون متغیرهای بالا تست‌ها `skip` می‌شوند (نه fail)، چون یک پوز ساختگی چیزی را که این تست
می‌سنجد — اینکه یک ضربهٔ صندوق‌دار و یک ضربهٔ آشپز همان سفارش را جابه‌جا می‌کنند — نمی‌تواند
وانمود کند.

### صداقت دربارهٔ اجرا

این تست‌ها در این محیط **اجرا نشده‌اند**: نه PHP، نه پایگاه‌دادهٔ زنده، نه مرورگر، و نه
توکن ورود به یک استقرار. آنچه انجام شده: `npx tsc -p tsconfig.e2e.json` بدون خطا
(`npm run typecheck:e2e`). تا وقتی یک نفر آن‌ها را روی استقرار واقعی سبز نبیند، این‌ها
«نوشته‌شده و typecheck شده‌اند»، نه «سبز».

همین موضوع برای تست‌های PHPUnit این مخزن صادق است: بدون PHP قابل اجرا نیستند و فقط از نظر نحو
بررسی شده‌اند.
